# SIMULATION_DESIGN.md — SIMULATION モードの設計

01 を 1 ゲーム通して自力でプレイし、暗算・アレンジ・セットアップの判断を学ぶモード。
CHECKOUT / SETUP / RECOVERY / MIXED / TRAINING とは **問題形式が根本的に違う**。

| | 既存モード | SIMULATION |
| --- | --- | --- |
| 出題 | アプリが場面を作る | 自分のプレイがそのまま場面になる |
| 回答 | 正解を選ぶ | 毎投の狙いを自分で決める |
| 着弾 | 自分で入力する | 能力に応じて自動で決まる |
| 得点 | アプリが計算する | 自分で暗算して入力する |
| 答え | その場で出す | **ゲーム中は一切出さない**（終了後にまとめて） |

## 2. 着弾シミュレーション

### 2-1. なぜ実寸ボードを別に持つのか

表示用の `geometry/dartboardGeometry.ts` は、スマートフォンでのタップ精度を
優先して BULL・トリプル・ダブルを実寸比より太く描いている
（例: トリプルリング幅が表示 20 に対し実寸 8 mm）。
この座標系で散布をかけると「実物の 2.5 倍の幅のトリプル」に当てることになり、
命中率が実戦とかけ離れる。

そこで **実寸（mm）のボードを唯一の物理モデル**とし、得点判定も実寸側で行う。

| リング | 実寸半径 (mm) | 表示半径 |
| --- | --- | --- |
| インナーブル（50） | 0 – 6.35 | 0 – 16 |
| アウターブル（25） | – 15.9 | – 34 |
| インナーシングル | – 99 | – 90 |
| トリプル | – 107 | – 110 |
| アウターシングル | – 162 | – 148 |
| ダブル | – 170 | – 170 |
| 盤面の外縁 | – 225.5 | – 205 |

実寸は WDF / PDC の標準ボード寸法（インナーブル直径 12.7 mm、
アウターブル直径 31.8 mm、トリプル / ダブルのリング幅 8 mm、
ダブル外周の直径 340 mm、盤面全体の直径 451 mm）による。
出典: <https://dartswdf.com/rules>

### 2-2. 表示位置と得点が食い違わないこと

`toDisplayPoint()` は **角度を変えず、半径だけを区間ごとに線形変換**する。
リングの境界どうしを対応させているので、実寸でトリプルなら表示でもトリプルになる。
「T20 と判定された着弾がシングルの位置に描かれる」ことは構造上起こらない。
2 万点の無作為着弾で一致を検証している（`boardGeometry.test.ts`）。

### 2-3. 1 投の流れ

```
狙った区画（タップ）
  → 狙い点（実寸 mm・その区画の中央）
  → σ をプレイヤー能力から決める
  → σx : σy をブレ方向で決める
  → 通常成分 or 低確率の大ミス成分で 2 次元正規乱数を加える
  → 着弾座標（実寸 mm）
  → 座標からリングとウェッジを判定 → 1 投の得点
```

得点ベースの固定確率表（「T20 なら ○% で 12」）は一切使っていない。
BULL もダブルも同じ 1 本の経路を通る。

**狙い点の例外**

- **ダブル**はリングの中央ではなく、内周から 1/4 の位置を狙う。中央を狙うと
  半径方向の誤差の半分がそのまま盤外へ出てしまい、実戦の「外すなら内側
  （シングル）へ外したい」という構えと合わないため。
- **BULL は内外を区別する**。DB（50 点）は中心そのもの、SB（25 点）はリングの
  半径の中ほど。アウターブルはドーナツ状で「中央」が一意に決まらないので、
  角度は真上（20 の方向）に固定する。どの角度でも SB であることは変わらず、
  決定論的であればよい。

  画面では、中心をタップすると DB・その外側のリングをタップすると SB になる
  （区画の描画は既存のまま。中心は DB の円が覆っている）。

### 2-4. 画面の表記

ターゲットは **略記だけ**で表す（`notation.ts`）。「トリプル20」のような読み下しはしない。

| 的 | 表記 |
| --- | --- |
| シングル 20 | `S20` |
| ダブル 20 | `D20` |
| トリプル 20 | `T20` |
| アウターブル（25 点） | `SB` |
| インナーブル（50 点） | `DB` |
| 盤外 | `MISS` |

`Dart.id` はほぼそのまま使えるが、インナーブルだけは内部 ID が `BULL` なので
`DB` へ読み替える。**内部 ID は変えない**（既存モード・データファイル・
テストフィクスチャと共有しているため）。表示だけの写像で、判定には一切影響しない。
おすすめルートの表示（`formatRoute` 由来の "T20 → T20 → BULL"）も同じ規則で
`T20 → T20 → DB` に直す。

## 3. 能力パラメータ

### 3-1. PPR → 散布幅 σ

First9 / Average の PPR は **的別の命中率へは変換しない**。
散布幅 σ（mm）を決めるためだけに使う。

σ は `accuracy.ts` のアンカー表（区間線形補間）で決まる。表は 2 つあり、
ゲーム全体用が `SIGMA_ANCHORS`、最初の 9 投用が `FIRST9_SIGMA_ANCHORS`（3-2 節）。
どちらも `npm run audit:simulation -- --solve` の逆算で作った。

> **逆算の手順**
> 「アプリのおすすめの 1 投目をそのまま狙う」固定戦略のプレイヤーに
> 501 を大量に投げさせ、実測の平均 PPR が目標値になる σ を二分探索する。
> ターゲット選択の揺れを混ぜないため、戦略は (残り, 残り本数) だけで
> 決まる決定論的な関数にしてある。

参考値（均等ブレ・最大ブレ中）: PPR 60 → σ 12.4 mm、PPR 100 → σ 5.7 mm。

- **PPR = 167 のときだけ σ = 0**。狙った的へ 100% 入る。
- **166 では σ > 0**。完全固定にはならない。
- 曲線は直線ではなく、低 PPR 側ほど σ の増え方が急になる。

### 3-2. First9 と Average の使い分け

| 投数 | 使う σ |
| --- | --- |
| 1 – 9 | First9 の σ（**First9 専用のアンカー表**） |
| 10 – 15 | First9 → Average へ 6 投かけて線形に遷移 |
| 16 – | Average の σ |

10 投目からの遷移は、9 投目と 10 投目で精度が不連続に飛ばないようにするためのもの。

**First9 のアンカー表はゲーム全体用と別に持つ。** 同じ σ でも、最初の 9 投の PPR と
ゲーム全体の PPR は一致しない。最初の 9 投は純粋な得点投げ（ダブル狙いも BUST も無い）
だが、ゲーム全体にはフィニッシュ狙いと BUST が入るぶん平均が下がるためで、
全体用の表をそのまま First9 に使うと **設定より 10〜15 点も高く出てしまう**
（設定 60 → 実測 73）。GAME REVIEW の FIRST 9 PPR が設定と食い違うので、
First9 は「最初の 9 投の PPR」を目標に逆算した `FIRST9_SIGMA_ANCHORS` を使う。
逆算の条件は全体用とまったく同じ。

Average が 167 のときは、ゲーム全体で σ = 0 にする（設問 10 の「Average のみ 100%」）。
First9 だけ 167 でも、10 投目以降は Average へ戻るので全体は 100% にならない。

開始点数を変えても、この設定の意味は **501 基準の PPR** のまま変えない。

### 3-3. ブレ方向

σx : σy の比を変える（σx · σy は一定に保つ）。

| 設定 | σx | σy |
| --- | --- | --- |
| 縦ブレ | σ / √2 | σ · √2 |
| 横ブレ | σ · √2 | σ / √2 |
| 均等 | σ | σ |

同じ σ でも、縦に広い散布はトリプル帯（幅 8 mm）を外しやすく、
横に広い散布はウェッジ（幅 18 度）の中に収まりやすい。
得点への影響が方向で大きく違うので、**σ のアンカー表は方向ごとに持つ**。
その結果、どの方向を選んでも設定 PPR と実測 PPR がほぼ一致する。

### 3-4. 最大ブレ

低確率で散布幅が跳ね上がる混合正規分布にする。

| 設定 | 大ミスの確率 | 倍率 |
| --- | --- | --- |
| 小 | 4% | 2.0 |
| 中 | 6% | 3.4 |
| 大 | 8% | 5.5 |

通常成分の σ は変えないので、「普段の精度」は最大ブレを上げても変わらず、
**たまに大きく外れる回数と外れ幅だけ**が増える。
得点は上限のある非線形な関数なので、平均 PPR は数点しか動かない
（大ほどわずかに下がる。監査で ±7 以内であることを確認している）。

### 3-5. 画面に出す設定説明（v1.4.1）

初見のユーザーが、各設定の意味と「何を基準に選ぶか」を読めるようにする。
設定画面そのものを長くしないため、**折りたたみ**（`<details>`）に入れる。
文言と数値は `engine/simulation/settingsGuide.ts` に集約する。

| 設定 | 意味 | 設定目安 |
| --- | --- | --- |
| FIRST 9 PPR | 開始から 9 投までの精度。高いほど序盤の着弾が狙いに近づく | ふだん 501 が何投で終わるか（PPR = 501 ÷ 投数 × 3） |
| AVERAGE PPR | ゲーム全体の精度。高いほど全体的に狙いへ集まる。167 のみ完全一致 | 同上 |
| ブレ方向 | 縦 = 盤面の上下へ散る / 横 = 盤面の左右へ散る / 均等 | 自分のグルーピングが盤面のどちら向きに伸びるか |
| 最大ブレ | 小 = 主に隣接エリア / 中 = たまに大きく外れる / 大 = 低確率で 2 つ隣や OUT BOARD | 自分がひどく外したとき、どこまで飛ぶか |

目安投数は PPR の定義から計算した値で、レーティングの対応表ではない
（`settingsGuide.test.ts` が 501 ÷ PPR × 3 との一致を検証している）。
盤外率は `npm run audit:simulation` の実測による。

**ブレ方向の説明は「盤面に対する上下・左右」で書く。** `scatterProfile()` は
σx / σy を**盤面に固定した XY 軸**へかけ、狙いの向きでは回転しない。
そのため「縦＝同じナンバー内・横＝隣のナンバー」が成り立つのは 20 や 3 のように
盤面の上下にあるナンバーを狙うときで、6 や 11 のように左右にあるナンバーでは
向きが入れ替わる。説明文にはこの但し書きを必ず入れる（テストで担保）。

## 4. 乱数と UNDO

ゲームの状態は乱数器そのものを持たず、**seed と「これまでに消費した回数」**だけを持つ。
1 投投げるたびに seed から消費回数ぶん空打ちして続きを引く。

この形にしてあるため:

- テストでは seed を固定すれば同じ着弾列を必ず再現できる
- UNDO は消費回数も 1 投ぶん戻すので、**同じ的を狙い直すと結果も同じ**になる
  （UNDO で結果を引き直す抜け道を作らない）

本番 UI に seed 入力は出さない（ゲーム開始時に乱数で決める）。

### UNDO の境界

| 状態 | UNDO |
| --- | --- |
| ラウンド途中（1〜2 投） | できる |
| 3 投そろった直後・暗算入力の前 | できる（入力画面から狙いへ戻る） |
| 暗算入力を確定したあと | **できない** |
| 前のラウンド | **できない** |

暗算入力の確定を境界にしているのは、そこで初めて「このラウンドの得点」が
確定した情報としてユーザーへ渡るため。そこから戻せると状態が合わなくなる。

### UNDO の置き場所（押し間違えの直し方）

盤面の区画は `path` を押した時点で 1 投として確定する（確認のワンタップは挟まない）。
スマートフォン縦画面では SVG が幅いっぱいに縮むため、T / D の帯は表示上 15〜20px 程度に
なり、指での押し間違えが起こり得る。そこで、直すための操作を盤面から離さない。

- 盤面の直後に「直前の 1 投」欄（`sim-last-throw`）を置き、**狙い**と**着弾**を並べる。
  得点は出さない（暗算のため）。1 投目の前は「外周の MISS 部分は狙えません」と案内する。
- その右に `1投戻す`（`sim-undo`）を置く。投擲の一覧や「中断する」より前。
- 得点の入力中（および BUST の表示中）は、「確定する前なら 1投戻す で直せる／確定後は戻せない」
  と入力欄の下へ書く。

盤面の当たり判定（`geometry/dartboardGeometry.ts`）・実寸の着弾モデル・UNDO の境界は変えていない。
指を置いて区画をプレビューし、離したときに確定する入力方式は、実機での誤入力率を
現行方式と比べてから採否を決める（測定前には入れない）。

## 5. ラウンド進行

- Double Out。BUST は `applyDart` の判定（残り点超過 / 残り 1 / ダブル以外で 0）。
- BUST はそのラウンドの得点をすべて無効にし、ラウンド開始時の残りへ戻す。
- **BUST のラウンドでは暗算入力を求めない**。3 投そろわないことがあり、
  「3 投の合計」が定義できないうえ、実際の得点は 0 で確定しているため。
- 3 投そろう / 上がる / BUST するとラウンドが終わる。
- 暗算入力が内部の得点と違えば「計算ミス」（内部の呼び名は CALCULATION MISS）としてその場で指摘し、
  **必ず内部の正しい得点で進める**。
- 上限 100 ラウンドで打ち切る（能力設定が極端でも必ず終わるようにする安全弁）。

### 5-1. 画面の LEFT と内部の残りを分ける

画面上部の LEFT は **ビジット開始時の残りで固定**し、1 投ごとには減らさない。
投げるたびに減らすと、残り点の暗算をアプリが肩代わりしてしまうため。
表示が新しい値へ変わるのは「得点を確定して次のビジットへ進んだとき」だけで、
3 投目の着弾直後や、正誤を確認している間もまだ変えない。

**これは表示だけの仕様。** 内部の残り（`ThrowRecord.leftBefore` / `leftAfter`、
`currentLeft()`）は従来どおり 1 投ごとに更新していて、BUST 判定・Checkout 判定・
Double Out 判定・履歴・GAME REVIEW・アレンジ / セットアップ判定はすべて
そちらを見ている。画面は `ActiveRound.leftBefore` を読むだけ。

3 投目より前に Checkout / BUST が確定した場合も、その時点でビジットが終わり
残りのダーツは投げられない。表示はビジット開始時の値のまま
（`LEFT 40` から `D20` で上がっても、途中で `LEFT 0` を出さない）。

### 5-1-2. 合計が合うまで次のビジットへ進まない

3 投の合計を間違えたら、**正しい合計を入れるまで次のビジットへ進めない**。
暗算そのものが練習なので、合っていない答えで先へは進めない。

- 間違えた入力は `ActiveRound.wrongEntries` へ積み、`entry` は null のままにする。
- 画面には「計算ミス」と「計算が間違っています」を出し、入力欄を空にして
  フォーカスを戻す。**正しい合計は教えない**（教えたら暗算にならない）。
- 正解した時点で `entry` が確定し、`wrongEntries` をそのまま持つ。
  GAME REVIEW の CALCULATION MISS は、この**間違えた回数の合計**で数える
  （1 ビジットで複数回間違えればそのぶん）。
- UNDO で投げ直すと合計が変わるので、`wrongEntries` も捨てる。

行き詰まったときは「中断する」でゲームを抜けられる。

### 5-2. 3 投終わったら、そのまま得点を打てる状態にする

3 投目が確定した瞬間に得点入力欄へフォーカスを移す。PC ではそのまま数字キーと
Enter で確定でき、スマートフォンでは `inputMode="numeric"` の欄に移るので
数字キーボードがそのまま開く。

フォーカスは `useLayoutEffect` から呼ぶ。盤面のタップという **ユーザー操作と同じ
処理の流れの中で** 呼ばないと、iOS Safari はソフトウェアキーボードを開かない。
`focus({ preventScroll: true })` で自動スクロールを抑え、そのうえで入力欄が
画面外のときだけ `scrollIntoView({ block: 'nearest' })` で最小限動かす
（見えているときは何も起きないので、盤面が飛ばない）。

UNDO の境界は変えない。3 投目のあとでも、得点を確定する前なら戻せる。
戻すと入力状態が解除され、3 投目を狙い直せる。

得点を確定したあとの「次のラウンドへ」も、キーボードだけで進められるように
ボタンへフォーカスを当てる。Enter / Space がそのまま押下になるので、独自の
キー処理を足さずに済み、読み上げの操作とも食い違わない。BUST のビジットでも同じ。

**1 投ごとの得点も画面には出さない。** 合計はもちろん、各投の点数を出してしまうと
暗算がただの足し算の読み上げになる。投擲リストに出すのは狙いと着弾、そして
BUST / CHECKOUT の印だけ。

## 6. レビュー

### 6-1. 評価するのは狙いだけ

`INTENDED TARGET` だけを評価対象にする。実際にどこへ刺さったかは使わない。

> 例: 残り 125 で T20 を狙って S5 へ飛んだ
> → T20 が妥当な狙いなら **判断は正しい**。着弾のミスは判断ミスに数えない。

同じ狙いなら着弾に関わらず判定が変わらないことをテストで担保している。

### 6-2. 判定の作り方

1 投ごとに `suggestFor(残り, そのビジットの残り本数)` を呼び、
**狙いを 1 投目に持つルートの推奨度**を見る。

| 条件 | 分類 |
| --- | --- |
| 残り 351 以上 | `SCORING`（アレンジ判断の対象外・得点を伸ばす場面） |
| 狙い通り入ると Bust する | `ARRANGEMENT MISTAKE` |
| ビジット最後の 1 投で Bogey を残す | `BOGEY CREATED` |
| MY ROUTE（得意ダブル）の 1 投目 | `GOOD DECISION` |
| 推奨度 S / A | `GOOD DECISION` |
| 推奨度 B | `BETTER OPTION AVAILABLE` |
| 推奨度 C | `ARRANGEMENT MISTAKE` / `SETUP MISTAKE` |
| 候補に無い狙い（CHECKOUT） | `ARRANGEMENT MISTAKE` |
| 候補に無い狙い（SETUP / NEXT VISIT） | `NOT EVALUATED`（断定しない） |

`ARRANGEMENT` と `SETUP` の別は、その場面が「この 3 投で上がる形」か
「次のラウンドへ残す形」かで決まる。

ただし **SETUP 側のビジット最後の 1 投だけ**は、この表より先に
「次のラウンドに 3 本で上がれる数字を作れるか」で判定する（6-2-3 節）。

### 6-2-1. 候補一覧の性質で扱いを変える

「候補一覧に無い」を **ミスの根拠にしてよいのは、その一覧が全候補を尽くしている
ときだけ**。この区別を間違えると、エンジンが評価していない狙いまで不正解にしてしまう。

| 場面 | 候補一覧 | 尽くしているか | 一覧に無い狙い |
| --- | --- | --- | --- |
| CHECKOUT（上がれる） | `rankCheckoutRoutes` | **はい**（全ルートの列挙） | `ARRANGEMENT MISTAKE` と断定できる |
| SETUP（171〜350） | `rankSetupRoutes` | いいえ（戦術のふるい＋件数上限） | `NOT EVALUATED`（おすすめだけ示す） |
| NEXT VISIT（上がれない） | `selectNextVisitProposals` | いいえ（最大 3 件の厳選） | `NOT EVALUATED`（同上） |

あわせて、SETUP ランキングへ渡す候補数は**表示件数（既定 40）で切らない**。
40 件は画面へ並べる数であって候補の全部ではなく、41 番目以降にある推奨度 S / A / B の
1 投目まで「候補に無い」と誤判定してしまう（171 の `T16 → S20 → T20` は推奨度 A）。

### 6-2-2. MY ROUTE と設定の渡し方

ユーザー設定は **PracticePage とまったく同じ渡し方**でエンジンへ写す。
得意ダブルは `fallbackPreferredDoubles`（NEXT VISIT だけが読む名前）で渡し、
`preferredDoubles` は `suggestFor` へ渡さない。そうしないと STANDARD / OTHER ROUTES の
順位が得意ダブルで動き、アプリが実際に表示した推奨とレビューの判定がずれる。

CHECKOUT では、それとは別に MY ROUTE（得意ダブルを優先し基準ルート加点を外した
ランキング）の 1 投目も計算し、それに沿った狙いは `GOOD DECISION` とする。
アプリが STANDARD と MY ROUTE を並べて出している以上、MY ROUTE に従った投げ方を
不正解にはしない。

**正解が一意ではない局面を不正解にしない**ため、
推奨度 A（＝非常に良い代替）は S と同じく GOOD DECISION として扱う。
既存の TRAINING の採点（成立する上がりは C ランクでも学習上の正解）と同じ思想。

`BOGEY CREATED` を **ビジット最後の 1 投に限る**のは、途中の投で一時的に
159 のような残りを通っても、同じビジットの残りのダーツで作り直せるため。
（例: 219 から T20 を狙うと一度 159 を通るが、これは正しい狙い。）

### 6-2-3. ビジット最後の 1 投は、別の軸で評価する（v1.4.1）

残り 1 投で「次のラウンドへ残す形」を作る場面は、推奨度だけでは足りない。
推奨度は**狙い通り入ったときの残り点の質**で決まるので、
シングルへ落ちたときにどうなるかが順位に入らない。

例: 残り 178 / 残り 1 投（推奨度はいずれも B）

| 狙い | 狙い通り | シングル落ち | 実戦での差 |
| --- | --- | --- | --- |
| T19 | 121（3 本で上がれる） | **159（Bogey）** | 外すと次のラウンドを失う |
| T20 | 118（3 本で上がれる） | 158（3 本で上がれる） | 外してもテンパイ |
| T18 | 124（3 本で上がれる） | 160（3 本で上がれる） | 外してもテンパイ |

SETUP エンジンのシングル落ち耐性（`isSingleMissTenpaiSafe`）は
**まだ投げ直せる本数がある場面**でだけ働くので、残り 1 本ではこの観点がどこにも無い。
エンジンは変えず、レビュー層（`engine/simulation/lastDartSetup.ts`）に
この場面ぶんの分析を持つ。

**評価軸は「次のラウンドに 3 本使って Checkout できる数字を作れるか」**。
160 や 170 のような特定の残り点は特別扱いしない。

| 狙い通り | シングル落ち | 分類 |
| --- | --- | --- |
| テンパイ | テンパイ | `GOOD DECISION`（※ 下の上位互換の場合を除く） |
| テンパイ | テンパイを外す（他に両立する的がある） | `BETTER OPTION AVAILABLE` |
| テンパイ | テンパイを外す（両立する的が無い残り点） | `GOOD DECISION` |
| Bogey | — | `BOGEY CREATED` |
| それ以外（170 を超える残りなど） | — | `SETUP MISTAKE` |

**※ 同じナンバーのトリプルが上位互換なら `BETTER OPTION AVAILABLE`（v1.4.2）**

シングル `Sn` を直接狙ってテンパイを作る選択は、悪手ではない。ただし
`Tn` の同ナンバーシングル落ちは **`Sn` を狙ったときと同じ残り**になるので、
`Tn` が次の 2 つを満たすとき、`Sn` を狙う理由が残らない（守りは同じで、
当たれば前進する）。

1. トリプルに入っても次のラウンドに 3 本で上がれる（Bust もしない）
2. シングルへ落ちてもテンパイを保てる（＝ `Sn` 狙いと同じ残り）

例（残り 178）:

| 狙い | 狙い通り | シングル落ち | 分類 |
| --- | --- | --- | --- |
| S18 | 160 | 160 | `BETTER OPTION AVAILABLE` |
| T18 | **124** | 160 | `GOOD DECISION` |
| S20 | 158 | 158 | `BETTER OPTION AVAILABLE` |
| T20 | **118** | 158 | `GOOD DECISION` |

条件を満たさなければシングル直接狙いは `GOOD DECISION` のまま
（例: 残り 171 の `S4` → 167。`T4` は 159 の Bogey なので上位互換ではない）。
**特定の残り点（160 / 170 など）は条件に入れない。**

この判定は **SETUP 帯（171 以上）だけ**に限る。170 以下は承認済みの
NEXT VISIT セレクタが残しを選ぶ場面で、そこでは残りが小さいほど良いとは
限らない（残り 41 の `S1` → 40 は D20 で上がれる残りで、`T1` → 38 が
上位互換とは言えない）。

説明文には、代わりに狙えるトリプルを**シングル落ちの残りまで添えて**最大 2 件出す。
並びは得点の高い順（同じ安全さなら点を稼げる的を先に出す）で、
1 つだけを絶対の正解にしない。

特に 181〜189 は、シングルへ落ちると 159〜169（Bogey が並ぶ帯）へ入りやすく、
この軸がそのまま次のラウンドの Checkout 機会になる。

適用しない場面（従来どおり推奨度で判定する）:

- この 1 投ではどの的でもテンパイを作れない残り点（比べる軸そのものが無い）
- BULL 狙い（外した 1 投の落ち先を「同ナンバーのシングル」と決められない）
- ダブル狙い（SETUP の得点手段として選ぶ的ではないので、この観点で
  良い判断へ引き上げない。悪い場合は従来の判定がそのまま拾う）
- 1 投目・2 投目（同じビジットの残りのダーツで作り直せる）

**エンジンの第 1 候補と食い違う場面**は、残り 2〜350 のうち 1 つだけ（残り 190）。
そこでは T10 → 160（S10 へ落ちると 180）よりも、
T20 → 130（S20 へ落ちても 170）の方がこの軸では良い。
アプリの推奨（S / A）を下げうるのはこの軸だけで、ランキングそのものは変更していない。

### 6-2-4. 表現の強さ

学習用途のモードなので、**悪い選択は悪いと分かる**言い方にする。
罵倒・煽り・感情的な表現は書かない。技術的・具体的・簡潔に書く。

| 分類 | 書き方 |
| --- | --- |
| `GOOD DECISION` | 何が良いのか（残り・シングル落ち）を事実で書く。他の妥当な狙いも添える |
| `BETTER OPTION AVAILABLE` | 「成立はしますが、良い選択ではありません」＋何がどう劣るか＋代案 |
| `ARRANGEMENT MISTAKE` / `SETUP MISTAKE` | 「この選択は不適切です」と言い切り、何を失ったかを書く |
| `BOGEY CREATED` | Bogey を作ったことと、次にどう考えるかを書く |

「成立する」と「良い選択」は必ず区別する。着弾のミスは判断ミスに数えない（6-1 節）。

### 6-3. Summary

開始点数 / 総投数 / PPR / FIRST 9 PPR / 計算ミスの回数 / BUST 回数 /
上がりのビジットの投数（`checkoutDarts`）/ 上がったビジットの開始残り（`checkoutScore`）。
PPR は BUST したラウンドの得点を 0 として数える（実戦の 3 ダーツ平均と同じ定義）。
上限の 100 ビジットで打ち切ったゲームは「上がっていない・未完了」と明示し、
上がったゲームと同じ見た目にしない。

### 6-4. 画面の表記

判断の分類の**内部キーと件数の数え方は変えず**、画面の表記だけを日本語にする
（`review.ts` の `THROW_VERDICT_JA` / `THROW_VERDICT_HINT_JA`）。

| 内部キー | 画面表記 | 補足（「判断の分類と用語の意味」に出す） |
| --- | --- | --- |
| `GOOD_DECISION` | 良い判断 | その場面で推奨できる狙い |
| `BETTER_OPTION_AVAILABLE` | もっと良い狙いあり | 成立はするが、もっと良い狙いがあった |
| `ARRANGEMENT_MISTAKE` | 上がり方を見直す | この 3 投で上がる形として不適切（狙い通りで BUST する狙いを含む） |
| `SETUP_MISTAKE` | 残し方を見直す | 次のビジットへ残す形として不適切 |
| `BOGEY_CREATED` | ボギーを残した | 最後の 1 投で、狙い通りでも次の 3 投で上がれない残りになる |
| `SCORING_PHASE` | 得点を伸ばす場面 | 残り 351 以上。採点していない |
| `NOT_EVALUATED` | 判定対象外 | 良し悪しを断定していない。良い・悪いのどちらにも数えない |

競技用語（CHECKOUT / BUST）・ターゲット表記（T20 / D20 / SB / DB）・PPR・推奨度・
MY ROUTE は英語のまま残し、`reviewGlossary.ts` の短い説明を折りたたみで添える。
推奨度の言葉（S = 基準推奨 など）は CHECKOUT のルートカードと同じ `data/gradeLabels.ts` を使う。
ゲーム中の表示（LEFT / ROUND / DART）は変えていない。

## 9. モデルの限界（正直に書いておく）

- 散布は **1 つの σ で等方向**（方向の比だけ変える）としている。
  実際の投げ手は「トリプル狙いのときとダブル狙いのときで精度が違う」が、
  ユーザーにダブル専用命中率を設定させない方針なので、その差は表現していない。
  そのため **ダブルを狙ったときの OUT BOARD 率は実戦よりやや高め**に出る。
- PPR のキャリブレーションは「固定戦略のプレイヤー」で行っている。
  実際のゲーム PPR は本人のアレンジ判断・ダブルの選び方・BUST でも動くので、
  設定値と完全一致はしない（監査では代表ケースで ±5 以内）。
- **SETUP の「候補に無い狙い」には判定を出さない。**
  SETUP / NEXT VISIT の候補は承認済みの戦術のふるいを通った一覧なので、
  そこに無い狙いは良いとも悪いとも言えない（6-2-1 節）。盤面の全 62 通りを
  総当たりで評価すれば断定はできるが、それは承認済みの戦術方針を
  レビュー側で上書きすることになるのでやらない。
- **エンジン側の候補数の上限（60 件）までは見えない。**
  `rankSetupRoutes` は内部で 60 件までしか評価しないので、それより下位にある
  良い 1 投目は候補一覧に現れない。既存エンジンを変えずに済ませるため
  この上限はそのままにし、「一覧に無い＝ミス」と言わないことで対処している。
- **残り 1 投の評価軸（6-2-3 節）は、レビュー層の分類方針**である
  （`docs/APPROVALS.md` A-20 に記録）。`docs/APPROVALS.md` の承認対象（基準ルート・
  重み・Bogey 定義など）には手を入れていないが、この軸だけはアプリの推奨度と
  別の観点なので、まれに推奨度 A の狙いを `BETTER OPTION AVAILABLE` にする
  （2〜350 の全残り点で、エンジンの第 1 候補と食い違うのは残り 190 の 1 件）。
- `SIGMA_ANCHORS` / `FIRST9_SIGMA_ANCHORS` は統計的に「正しい」値ではなく、
  **このアプリでの妥当な基準として選んだ暫定値**である。
  戦術データ（`docs/APPROVALS.md`）とは別物で、
  変えたい場合は `--solve` で逆算し直して差し替える。
