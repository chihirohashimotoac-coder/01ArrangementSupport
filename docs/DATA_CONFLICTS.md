## QUESTION #2 — S-BULL 調整例（231〜235 / 271〜275）と engine の最上位候補が異なる

**種別**: 戦術判断
**状態**: **解決済み（2026-08-31 人間承認 / APPROVALS.md A-2）**。データは無変更。

資料 (6) の S-BULL 調整例は、**算術・ルールとしてはすべて正しい**ことを検算済みです
（10 件すべてで、合計・残り・テンパイ成立を確認）。

一方、engine が同じ残り点で最上位に置く候補は資料と異なります。

| 残り | 資料の例 | 残り | engine の最上位 | 残り |
| --- | --- | ---: | --- | ---: |
| 231 | S20 + S19 + SB（64点） | 167 | T20 + T20 + S20（140点） | 91 |
| 271 | T19 + S19 + SB（101点） | 170 | T20 + T20 + T20（180点） | 91 |

**理由**: 91 は 2 本でも上がれ（T17 + D20）、上がりが D20 で、BULL を要求しません。
残りの質としては 167 / 170 より高く評価されます。加えて取得点も大きく上回ります。

**解釈**: 資料 (6) は「トリプルを使わなくても S-BULL で着地を整えられる」という
**技術の説明**であって、「その組み立てが常に最善である」という主張ではないと読めます
（実際、資料には「1本目に60が入った後」という前提が併記されています）。

**対応**: 資料の値はフィクスチャ（`src/data/setupReferenceCases.ts`）として保持し、
算術・ルール・テンパイ成立をテストしています。engine のランキングとの一致は要求していません。

**判断（2026-08-31）**: これらの例は「常に最適なルート」ではなく、
**S-BULL を利用した SETUP 調整技術の教材例**として扱うことが承認されました。
engine のランキングを資料に合わせる変更は行いません。
資料・フィクスチャ・ランキングのいずれも無変更です。

## NOTE #3 — 「180 後にテンパイになるのは下一桁が 0・1・4・7」の適用範囲

**種別**: 経験則の範囲
**状態**: **解決済み（2026-08-31 人間承認 / APPROVALS.md A-3）**。資料・実装とも無変更。

資料 (3) に「180後にテンパイになるのは下一桁が **0・1・4・7** のとき／
**2・3・5・6・8・9** はテンパイにならない」とあります。

これは **340 点台（= 残り 159〜170 の帯）では正しい**ことを検算済みです。
ただし一般の残り点には拡張できません。反例:

- 152（下一桁 2）→ T20 + T20 + D16 で 3 本チェックアウト可能
- 158（下一桁 8）→ T20 + T20 + D19 で 3 本チェックアウト可能

**対応**: `LAST_DIGIT_RULE_BAND = { min: 159, max: 170 }` として帯を明示し、
`hasMemorableLastDigit()` は帯の内側でだけ true を返します。
加点も +6 と小さくし、実際の判定は engine の計算に委ねています。
UI の説明文にも「この帯に限った経験則です」と明記しています。

**資料の修正は不要**です（資料は 340 点台の文脈で書かれているため、その範囲では正しい）。

**判断（2026-08-31）**: 「下一桁 0・1・4・7」は **159〜170 付近の対象帯に限定した教材ルール**
として扱うことが承認されました。一般の残り点へは拡張しません。

## NOTE #4 — Excel の収録範囲（41〜170 の 123 件）


## RESOLVED #5 — LEFT 2〜40 の基準ルート

**種別**: 導出データの承認
**状態**: **承認済み（2026-08-31 / APPROVALS.md A-4）— 39 件**

Excel は 41〜170 しか収録していないため、2〜40 は明示ルールで導出しています。
ルールと導出結果は `docs/CHECKOUT_DATA_POLICY.md` §5 を参照してください。

**判断（2026-08-31）**: 現在の導出規則を **v1 の STANDARD 基準ルートとして承認**。
`reviewStatus` を `human-approved-v1` へ変更しました。導出結果そのものは無変更です。

承認された内容（いずれも v1 の暫定方針であり、唯一の正解ではありません）:

1. 奇数の残りは「32 → 16 → 8 → 4 → 2」の順に立て直しやすいダブルを作る
2. 31 は `S15 + D8`（`S7 + D12` を好む流儀もあるが、v1 では前者を採る）
3. 偶数はすべて 1 本上がり（`D(LEFT/2)`）。38 → D19 のように奇数ダブルになる場合も含む

見直したくなった場合は、このファイルへ `PROPOSED CHANGE` を書き、
`docs/APPROVALS.md` へ v2 として追記したうえで人間の承認を得てください。

## QUESTION #7 — 設定画面の「PDC で頻出する実戦的なアレンジ」という表現

**種別**: 名称・出典
**状態**: **解決済み（2026-08-31 人間判断）**。出典中立の表現へ差し替え済み。

v1.1（入力 UX 改善 PR）の依頼で、設定画面の説明文を次の文言にするよう指示がありました。

> STANDARD（基準ルート）は、PDC で頻出する実戦的なアレンジをベースにしています。

依頼では「PDC 公式ルート」「PDC 公式が定めたルート」と書かないことも同時に指示されており、
**公式性は主張していません**。また `STANDARD` /「基準ルート」という**呼称そのものは変更していません**
（`APPROVALS.md` A-1 の対象は呼称です）。

一方で `APPROVALS.md` A-1 は、「PDC頻出ルート」という表記を採らない理由として
**「出典の一次資料が確認できていないため」**を挙げています。
「PDC で頻出する」という記述は頻度についての出典主張にあたるため、
A-1 の趣旨と緊張関係があります（PR #2 の自動レビューでも P1 として指摘されました）。

**判断（2026-08-31）**: リポジトリオーナーより **出典中立の表現へ差し替える**方針が示され、
次の文言へ変更しました。

> STANDARD（基準ルート）は、実戦で使われる標準的なアレンジをまとめたものです。
> MY ROUTE では、設定した得意ダブルを考慮した候補を表示します。

`APPROVALS.md` A-1（出典の一次資料が確認できるまで PDC への帰属を主張しない）を
**そのまま維持**する判断です。A-1 の変更や v2 の追記は行っていません。

ユーザー画面から出典の主張が消えたことを回帰テストで固定しています。

- `src/App.test.tsx`: 設定画面の説明に `PDC` / `公式` が現れないこと
- `e2e/app.spec.ts`: 設定画面全体に `PDC` が現れないこと

一次資料が確認できた場合にかぎり、`APPROVALS.md` へ v2 として追記したうえで
出典に言及する表現を検討してください。
